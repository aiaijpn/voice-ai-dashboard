ADR-018

開発ブランチ運用と Render 本番分離方針

Status

Accepted

Date

2026-03-16

背景

栄一ツールは現在まだ 本番運用前の開発段階である。

この段階では

開発速度を落とさない

実験をしやすくする

退避点を残す

将来の本番環境分離に備える

ことが重要である。

一方で、Render が単一構成のまま本番運用に入ると

開発コードがそのまま本番に反映される

本番BOTへ影響する

というリスクがある。

したがって、

開発段階のブランチ運用

将来の本番分離

を整理しておく必要がある。

問題

以下の2点を整理する必要がある。

1

GitHubブランチをどの粒度で作るか

2

将来、本番環境をどう分離するか

もし細かくブランチを切りすぎると

開発が遅くなる

管理が複雑になる

一方で、退避点が無いと

比較ができない

安定点に戻れない

という問題が発生する。

決定

当面は次の方針を採用する。

1. main を開発本線とする

当面の開発は

main

で進める。

つまり

main = 開発本線

とする。

この段階では

main = 本番

とは扱わない。

2. ブランチは M進捗時に作る

比較点・退避点として

release/v1-xxxx

ブランチを作成する。

ただし ADR作成時ではなく

M進捗時に作る。

対象

M1 完了
M2 完了
M3 完了
M4 完了

例

release/v1-m1
release/v1-m2
release/v1-m3
release/v1-m4

このブランチは

比較

退避

挙動確認

のために保持する。

3. ADRではブランチを切らない

ADRは

設計決定の記録

であり、

実装進捗

とは一致しない。

そのため

ADR作成 = ブランチ作成

とはしない。

4. バックアップリポジトリを保持する

別リポジトリとして

voice-ai-dashboard-v1-backup

を保持する。

用途

安定版退避

緊急復旧

比較

このリポジトリは

原則更新しない

凍結保存とする。

5. 本番開始時は Render を分離する

本番環境開始時には

開発環境
本番環境

を分離する。

その際

Render も

開発Render
本番Render

の 2本構成にする。

理由

GitHubのみ分離しても

Render が1本の場合

開発変更
↓
本番反映

が起こるため。

採用後の構成
開発段階
GitHub

voice-ai-dashboard
├ main
├ release/v1-m1
├ release/v1-m2
├ release/v1-m3
└ release/v1-m4

backup repo
voice-ai-dashboard-v1-backup
└ main
本番開始後
GitHub
voice-ai-dashboard
├ main
├ release/...
└ ...

Render
├ development
└ production
効果

この方針により

開発を軽く進められる

節目比較ができる

安定点へ戻れる

将来の本番分離が容易

となる。

補足

このADRは

開発段階の運用ADR

である。

本番運用開始時には

デプロイ運用ADR

Render分離ADR

本番反映手順ADR

を追加する予定である。
